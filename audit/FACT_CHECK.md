# Factual review — 25 October 2026

## Scope and status

**This is a targeted factual audit with a complete file inventory, not a completed verification of every fact.** The repository contains 76 content files (3,758,822 bytes), 734 examination cards, 816 terminology cards, 73 SQL exercises, 109 calculation exercises, and 30 diagram exercises. Each file is fingerprinted in [content-inventory.json](content-inventory.json). A file being inventoried, parsed, or tested does not mean its statements have been independently verified.

Reviewed the content architecture, selected lesson passages and their duplicated glossary/card content, mathematical examples, navigation, dashboard, flashcard setup, sources, and assessment implementation. Checked high-risk legal and technical statements against the primary sources linked below. App code and learning content were left unchanged.

Validation: `npm.cmd test -- --reporter=dot` passed **84 test files / 1,271 tests**. These cover parsing, behavior, calculations, SQL, links between content, and rendering syntax; they do not establish that every explanation or answer is true. There were non-failing Vite configuration warnings and KaTeX euro-character metric warnings. No browser surface was available through the UI tool, so design observations are based on source inspection, not a new visual or usability test. Yesterday's `VERBESSERUNGEN.md` is supporting historical context, not fresh verification.

The checked-in `content/` copy is the audited corpus. Local mode can load a different directory through `LERN_QUELLE`; those external contents and generated AI answers are outside this snapshot.

## What the current verification system misses

`server/quellenPruefen.ts` checks HTTP responses. `shared/quellen.ts` checks URL shape and whether a target exists. Neither determines whether the page supports the attached explanation. `geprueft: 2026-10` is too ambiguous to mean “fact checked.” The 393 references include 342 Studyflix/Wikipedia entries; these can remain useful learning resources, but legal and technical claims should have direct primary evidence.

The SQL checker compares result sets on supplied datasets. Passing that check is useful evidence for those datasets, not a proof of universal SQL equivalence or of the prose explanation. SQLite also accepts some SQL that other systems reject; retain dialect warnings and independently review exam-facing rules. [SQLite aggregate-query extensions](https://www.sqlite.org/lang_select.html#bareagg).

Mathematical typesetting checks detect invalid KaTeX, not false formulas or missing assumptions. Even sound property tests can pass while a description such as F05 remains wrong.

## Remaining work required to honestly finish “every fact”

1. Split each lesson paragraph/table row, glossary entry, card question/answer, solution, diagram explanation, formula description, and factual UI message into atomic claims. Keep false quiz options marked as distractors, not app assertions. Store a stable ID and content hash for each claim; preserve card IDs used by saved progress.
2. Give each claim one explicit status: `unreviewed`, `verified`, `qualified`, `incorrect`, `unsupported`, or `not-a-factual-claim`. Record the exact source passage/section, source date/version, review date, assumptions, and all dependent occurrences. Do not label a whole page verified after checking one sentence.
3. Finish legal/exam claims first: all WiSo solutions, eligibility and exception rules, payroll thresholds, GDPR/BDSG, NIS2, AI Act, examination dates, permitted aids, and jurisdiction-specific IHK instructions. In particular, the alleged June-2026 working-time bill, Digital Omnibus status, actual GKV average, current DPF litigation, and all November exam-date references remain open here. Do not replace uncertain current-law statements with guesses.
4. Independently recompute **every** fixed exercise answer from its inputs. Cover statistics, regression, classification, probability, neural networks, process metrics, costing, project networks, availability, and backup examples. Use independently derived expected values rather than the implementation under review as its own oracle. Explicitly handle zero denominators, negative values, rounding, units, and quantile conventions.
5. Execute and inspect every SQL example against its intended schema; test NULLs, ties, duplicate rows, empty groups and unseen rows. Review reference-query intent separately from successful execution. Check every diagram's notation and each allowed answer against the relevant standard/version.
6. Review the remaining 1,550 card answers and terminology pages against their sources, including generated multiple-choice alternatives. Search synonymous and paraphrased duplicates, not only exact strings.
7. Review UI claims: meaning of “known,” “due,” “solved,” score rounding, mastery and exam readiness, local/online storage, backups, offline availability, and optional external requests. Behavior tests support these but do not substitute for an end-to-end review.
8. Only declare completion when **every inventoried claim** has a disposition and evidence, every confirmed correction has propagated to its dependencies, and no high-priority unresolved claims remain. A changed claim hash must invalidate its earlier verification.

## Reproduce the inventory

Run `node audit/scan-content.mjs` from the repository. It reads every checked-in content file, records hashes and counts, independently recomputes selected examples, and writes `audit/content-inventory.json`. Finding IDs beginning with `F` refer to the table above; `V01` is a verified example; `R01` marks material requiring further current-law review. Matching a search rule is not proof of an error, and absence of a match is not verification. The script does not fetch websites or change app content.
